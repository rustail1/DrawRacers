# 70 — ENVIRONMENT / PLATFORM ID / ASSET REGISTRY CONTRACT
Статус: **DEPLOYMENT DATA SOURCE-OF-TRUTH v1.3.4**.

Цель: actual IDs появляются только после Roblox provisioning/upload. Чтобы никто не спрашивал «куда записать PlaceId/ProductId/AssetId и какой из них настоящий», все deployment IDs имеют один owner — этот registry contract + environment config generated from it.

## 1. No fake IDs
Pre-production docs never invent numeric Roblox IDs. Numeric IDs are generated by platform and filled after provisioning. Missing required PROD ID = release blocker, not permission to type a placeholder.

## 2. Registry files in repository
Create deployment files outside gameplay design:
```text
config/deploy/dev.env.lua
config/deploy/staging.env.lua
config/deploy/prod.env.lua
assets/asset_registry.lua
```
Secrets/tokens are never committed. These files contain public platform IDs/config only.

## 3. EnvironmentConfig exact keys
Each environment config exports:
```text
EnvironmentName
UniverseId
EntryFTUEPlaceId
RacePlaceId
PlaceModeById
DataStoreNamespace
AnalyticsEnvironment
MonetizationEnabled
BotsEnabled
StarterStylePassId
NeonStylePassId
PremiumPresentationPassId
Coins450ProductId
Coins1100ProductId
Coins2500ProductId
```
Rules:
- DEV/STAGING namespaces differ from PROD;
- `MonetizationEnabled=false` in EntryFTUEPlace regardless of environment;
- Coin Developer Products remain disabled by feature flag until `61` condition;
- unknown/missing enabled SKU fails closed.

## 4. Asset registry schema
Each semantic asset entry:
```text
Key
AssetType
AssetId
Owner
SourcePath
SourceHash
LicenseOrOriginal
ModerationState
RuntimeUse
ReleaseRequired
```
Canonical keys include all cosmetics in `62`, all audio keys in `47`, UI icon set, logo, theme kits if uploaded assets, VFX assets and discovery assets where platform ID is relevant.

## 5. Runtime rule
Gameplay code references semantic keys/config. It never contains raw numeric SoundId/ImageId/MeshId/ProductId/PassId except generated deployment binding layer. One platform ID change must not require gameplay code edit.

## 6. Validation at boot
Server boot validates:
- current PlaceId maps to known PlaceMode;
- required environment IDs are nonzero/valid format;
- enabled monetization IDs resolve to known SkuKey;
- exact canonical ItemIds resolve;
- feature flags compatible with environment (no PROD rewards in DEV namespace etc.).
Critical mismatch fails closed and logs observable deployment incident.

Client validates presentation assets lazily with fallback; missing cosmetic visual must never alter physics.

## 7. Change procedure
When an asset/SKU/place is replaced:
1. update registry/environment file;
2. retain old mapping in Git history, not duplicate current owner;
3. run staging smoke;
4. if player-owned entitlement mapping changes, write migration/compatibility plan before PROD;
5. deploy compatible pair of places.

## 8. Production completion table
Before public release every row below must be RESOLVED:
- PROD UniverseId;
- EntryFTUEPlaceId;
- RacePlaceId;
- 3 Pass IDs;
- 3 Developer Product IDs (may be disabled but IDs provisioned);
- all 20 produced cosmetic visual assets where platform IDs are used;
- 2 music + all required SFX;
- logo/icon/thumbnails;
- required UI icons/images;
- environment DataStore namespace;
- analytics environment label.

## 9. Acceptance
PASS when no raw deployment ID exists outside registry/generated binding layer, STAGING/PROD configs differ correctly, all required PROD IDs are resolved, disabled SKUs cannot prompt, missing ID fails closed, and asset registry provenance agrees with `48/69`.
